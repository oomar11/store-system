# تقرير مراجعة النظام — أغسطس 2026

مراجعة معمارية وتشغيلية للتطبيقات الثلاثة: **المحل** (`store-system`) · **ورشة PVC** (`aa`) · **ورشة البلسية** (`plisse-workshop`).

التاريخ: 13 أغسطس 2026  
نوع المراجعة: تحليل كود + فحص لينكات الإنتاج العامة (بدون دخول حسابات وبدون قراءة بيانات عملاء).

---

## 1. ملخص تنفيذي

النظام مصمم صح من ناحية الفكرة: **المحل هو مصدر الحقيقة للنقد والعملاء وكشف الحساب الموحّد**، والورشتين بتشتغلوا شغلهم المحلي (تصنيع / فواتير / مقايسات) وبيبعوا القيود والخزنة على المحل عبر جسر (`/api/workshop/*`).

المشكلة الأساسية مش إن الجسر مش موجود — الجسر موجود ويشتغل — المشكلة إن **كل تطبيق بيعرض فلوس العميل بقانون مختلف**، والورشتين **ما بيقرؤوش كشف المحل**. النتيجة: نفس الشخص ممكن يشوف متبقي في البلسية، متبقي تاني في PVC، ورصيد تالت في المحل.

كمان فيه فجوات أمنية وتشغيلية لازم تتعالج قبل أي توسع: مفتاح الجسر مكتوب في الكود، ورشة PVC مفيهاش تسجيل دخول وواجهة `/api/store` مفتوحة، وورشة البلسية ليها رابطين إنتاج بسلوك مختلف.

### أهم النتائج في سطر

| الموضوع | الوضع الحالي |
|---------|----------------|
| مصدر الحقيقة المقصود | المحل: نقد + عملاء + أستاذ عبر البرامج |
| اللي بتتشاف في الورشتين | دفاتر محلية فقط (ما عدا أرصدة الخزن وشارات خطوط الشغل) |
| كشف الحساب الموحّد | موجود في المحل، الورشتين **ما بيستدعوهوش** |
| مزامنة الفشل | الكتابة المحلية تنجح أولاً؛ فشل الجسر يسيب الدفاتر مختلفة |
| أمان الورشتين | ضعيف جداً (PVC بدون auth · بلسية anon مفتوح على الدومين الصحيح) |
| مفتاح الجسر على الإنتاج | الورشتين شغالين بـ **fallback** مش متغير بيئة |

## 2. حدود المراجعة — إيه اللي اتشاف وإيه اللي محتاج أكسيس

اتعمل من غير ما نلمس بيانات عملاء حية:

- قراءة كود المستودعات الثلاثة بالكامل (مسارات، جداول، جسر، حسابات المتبقي).
- فحص لينكات عامة:
  - المحل: `https://store-system-rho.vercel.app` — شغال، جسر مضبوط، تيليجرام مضبوط.
  - PVC: `https://aa-omega-wine.vercel.app` — شغال، Postgres دائم، revision 1056.
  - بلسية: `https://plisse-workshop-sigma.vercel.app` — مفتوح بدون دخول.
  - بلسية (الرابط القديم في README): `https://plisse-workshop.vercel.app` — يحوّل لصفحة `/login`.

**ما اتعملش** (محتاج أكسيس صريح منك قبل ما نكمّل مقارنة أرقام حية):

1. دخول حساب مالك على المحل (أو صلاحية Supabase SQL) لمقارنة أرصدة عملاء معيّنين بين الشاشات.
2. صلاحية MCP لـ Supabase / Vercel (الاتنين `needsAuth` في البيئة دي).
3. استعلام Neon/Postgres لورشة PVC — `/api/store` مفتوح بس **ما سحبتش منه بيانات العملاء** لأنها بيانات شخصية.
4. حسابات دخول لرابط البلسية اللي بيطلب login (`plisse-workshop.vercel.app`).

لو حابب المرحلة الجاية تكون مطابقة أرقام عميل بعميل، ابعت: دخول محل (أو SQL read-only) + اسم/تليفون 2–3 عملاء ليهم حركة في أكتر من تطبيق.

## 3. خريطة النظام

```
┌─────────────────────┐     جسر ورشة      ┌──────────────────────────┐
│  ورشة PVC (aa)      │ ───────────────► │                          │
│  Next.js + Neon KV  │  بيع / تحصيل /   │   المحل (store-system)   │
│  بدون تسجيل دخول    │  خزنة / خامات    │   Supabase + Auth        │
└─────────────────────┘                  │   مصدر الحقيقة للنقد     │
                                         │   والعملاء والموردين     │
┌─────────────────────┐     جسر ورشة      │                          │
│  ورشة البلسية       │ ───────────────► │   جداول الربط:           │
│  Next.js + pls_*    │  عميل / بيع /    │   workshop_party_map     │
│  AUTH_DISABLED      │  تحصيل / خزنة    │   cross_app_ledger_entries│
└─────────────────────┘                  │   workshop_invoice_inbox │
                                         └──────────────────────────┘
```

| التطبيق | رابط الإنتاج المعتمد | قاعدة البيانات | تسجيل الدخول |
|---------|----------------------|-----------------|---------------|
| المحل | `store-system-rho.vercel.app` | Supabase (جداول المحل) | نعم (مالك / مدير / موظف) |
| PVC | `aa-omega-wine.vercel.app` | Neon Postgres كـ JSON KV | **لا** |
| البلسية | `plisse-workshop-sigma.vercel.app` | نفس مشروع Supabase بجداول `pls_*` | **معطّل** على الدومين ده |

الورشتين بيتكلّموا مع المحل من السيرفر عبر `/api/store-bridge/*` بمفتاح `WORKSHOP_BRIDGE_SECRET`. المتصفح ما المفروض يشوفش المفتاح الحقيقي.

## 4. حركة البيانات والتواصل بين التطبيقات

### 4.1 إيه اللي بيتحرك فعلياً

كل عملية مالية مهمة من الورشة = **كتابة محلية + دفع للمحل**. المحل بيستقبل عن طريق APIs تحت `/api/workshop/`.

| الحدث | PVC (aa) | البلسية | أثره في المحل |
|--------|----------|---------|----------------|
| إنشاء / تعديل عميل | `POST /parties/customers` | نفس المسار | upsert في `customers` + صف في `workshop_party_map` |
| بيع شغل | `POST /parties/ledger` (`sale:{projectId}`) لما المشروع يبقى مش مقايسة | `POST /parties/ledger` (`inv:{invoiceId}`) مع إنشاء الفاتورة | قيد `workshop_sale` + زيادة `customers.balance` |
| تحصيل / عربون | خزنة `safe-movement` deposit + قيد `workshop_collection` | نفس الفكرة | حركة خزنة + نقص رصيد العميل |
| إلغاء / حذف دفعة | خزنة بمبلغ 0 + `workshop_void` | نفس الفكرة | عكس الحركة |
| صرف خامات من مخزون المحل | `POST /issue` | **غير مستخدم** | فاتورة بيع «للورشة»: مخزون ينقص، **من غير خزنة ومن غير ذمة عميل** + صف في صندوق الوارد |
| توريد خارجي / مصروف آجل | `POST /purchases` | **غير مستخدم** | فاتورة شراء على مورد |
| مصروف نقدي من الورشة | سحب خزنة | — | نقص خزنة المحل |
| كشف حساب موحّد | **مش مستدعى** | **مش مستدعى** | `GET /parties/statement` موجود بس الورشتين مش بيستخدموه |

`source_system` بيتميز: `"aa"` أو `"plisse"`. المفتاح التكراري في الدفتر: `(source_system, source_ref)` — إعادة الإرسال آمنة نظرياً.

### 4.2 إيه اللي **ما بيتحركش**

- أرصدة العملاء **من المحل رجوع للورشة** (الورشة مش بتقرأ الكشف).
- كتالوج خامات PVC ↔ أصناف مخزون المحل.
- فواتير شغل الورشة **مش** فواتير بيع في شاشة `/sales` — بتظهر كقيود على حساب العميل فقط.
- حذف عميل من PVC **ما بيفكش** الربط في المحل.
- تقارير المحل (`/reports`) **ما بتشملش** قيود `cross_app_ledger_entries` — مبيعات الورشة مش جوه تقرير المبيعات.

### 4.3 مسارين منفصلين: الذمة vs النقد

التحصيل من الورشة = طلبين مستقلين:

1. `POST /parties/ledger` → رصيد العميل  
2. `POST /safe-movement` → رصيد الخزنة  

لو واحد نجح والتاني فشل، المحل يشوف عميل اتسدد من غير فلوس دخلت الخزنة، أو العكس. مفيش طابور إعادة محاولة تلقائي.

### 4.4 ربط العملاء (دمج الأطراف)

المحل ما عندوش جدول «عملاء ورشة» منفصل. العميل الواحد في `customers`:

1. لو فيه `workshop_party_map` لنفس `(source_system, local_party_id)` → يتحدّث نفس الصف.
2. وإلا مطابقة **بالتليفون فقط** (آخر 9–10 أرقام). **مش بالاسم** (اتصلحت بعد دمج غلط لعملاء اسمهم «عمر»).
3. وإلا عميل جديد.

لو التليفون فاضي أو مختلف → نفس الشخص يظهر مرتين في المحل. لو التليفون مشترك → شخصين يندمجوا غلط. أدوات الإصلاح موجودة في إعدادات جسر الورشة (`/api/workshop/party-maps`).

## 5. مقارنة البيانات المعروضة

ده أهم جزء عملي: **نفس الرقم اسمه «متبقي» في كل تطبيق، ومعناه مختلف.**

### 5.1 قانون المتبقي / الرصيد

| الشاشة | القانون | يشمل شغل تحت التنفيذ؟ | يشمل محل + الورشة التانية؟ |
|--------|---------|------------------------|------------------------------|
| PVC قائمة العملاء | مجموع (بيع − مدفوع) للمشاريع **`workflow === done` فقط** | لا | لا |
| PVC الحسابات «الباقي عند العملاء» | نفس القانون | لا | لا |
| PVC مشروع لسه في الانتظار / الورشة | البيع والمدفوع موجودين في حساب المشروع، **مش** في متبقي العميل | — | لا |
| البلسية الرئيسية / العملاء / الفاتورة | `max(0, total − paid)` لكل فاتورة غير ملغاة | نعم (حتى لو pending) | لا |
| المحل `customers.balance` | رصيد العمود بعد كل قيود الجسر + فواتير المحل الآجلة | نعم (بيع PVC بيتسجل من أول عربون) | **نعم** |
| المحل كشف الحساب / طباعة | دمج فواتير محل + دفعات + قيود PVC + قيود بلسية (+ مورد مربوط لو موجود) | نعم | نعم |
| المحل `/receivables` | متبقي لكل مشروع/فاتورة من دفتر الجسر + مبيعات محل آجلة | نعم | نعم |

### 5.2 مثال يوضح التعارض

عميل عنده مشروع PVC اتقفل عربون ودخل الورشة، ولسه مش `done`، وعنده فاتورة بلسية، واشترى من المحل بالأجل:

| التطبيق | اللي هيشوفه المستخدم |
|---------|----------------------|
| PVC | المتبقي = **صفر** (المشروع مش مكتمل تصنيعاً) |
| البلسية | متبقي فاتورة البلسية فقط |
| المحل | رصيد = متبقي PVC (البيع − العربون) **+** متبقي البلسية **+** أجل المحل |

ده مش باج في الجسر — ده **ثلاث تعريفات مختلفة لنفس الكلمة**. المستخدم هيظن إن في تطبيق «غالطان».

### 5.3 جدول تفصيلي: إيه ظاهر فين

| البيان | PVC | البلسية | المحل |
|--------|-----|---------|-------|
| قائمة العملاء المحلية | نعم | نعم | نعم (جدول موحّد) |
| رصيد العميل المحلي | متبقي شغل مكتمل فقط | مجموع فواتير غير ملغاة | `customers.balance` (كل المصادر) |
| شارات سلك / محل / ورشة | نعم (من المحل) | نعم (من المحل) | نعم |
| كشف حساب موحّد | لا | لا | نعم |
| أرصدة الخزن | نعم (من المحل) | نعم (من المحل) | نعم |
| حركات الخزنة | لا (بتتكتب بس) | لا | نعم `/treasury` |
| فواتير شغل الورشة في `/sales` | — | — | **لا** (قيود دفتر فقط) |
| صرف خامات / مخزون | صرف من مخزون المحل على مشروع | لا | فاتورة «للورشة» + صندوق وارد |
| كتالوج الخامات / أسعار القطاعات | محلي (مش مخزون) | 13 صنف محلي | أصناف المخزون |
| أوامر تشغيل / قص | لا بنفس شكل البلسية | نعم | لا |
| مصروفات الورشة | محلي + خزنة/مورد | لا | تظهر كخزنة أو فاتورة شراء |
| تقارير الربح | محلي (بيع − مصروف المشروع) | لا | تقارير محل **بدون** مبيعات الورشة في دفتر الجسر |

### 5.4 فواتير «للورشة» من نقطة البيع

لما المحل يبيع «للورشة»:

- المخزون ينقص والفاتورة تقفل مدفوعة بالكامل (بدون خزنة وبدون ذمة عميل).
- الصف يدخل `workshop_invoice_inbox`.
- PVC تقدر تخصمها على مشروع كمصروف.
- **ما تزودش** `customers.balance`.

يعني تكلفة الخامات على المشروع في PVC ≠ ذمة على العميل في المحل. ده مقصود تشغيلياً، بس لازم يبقى واضح في التقارير وإلا الربحية هتتلخبط.

## 6. المشاكل

مقسّمة حسب الخطورة. P0 = أمن/تشغيل ينفع يكسر ثقة الأرقام أو يسرّب بيانات.

### P0 — أمن وموثوقية الربط

1. **مفتاح جسر الإنتاج مكتوب في كود الورشتين**  
   `PRODUCTION_BRIDGE_SECRET_FALLBACK` في:
   - `aa/lib/store-bridge-server.ts`
   - `plisse-workshop/src/lib/store-bridge-server.ts`  
   فحص الإنتاج رجّع `"source":"fallback"` للاتنين — يعني متغير `WORKSHOP_BRIDGE_SECRET` **مش متضبط على Vercel**. أي حد يقرأ المستودع يقدر ينادي APIs المحل (خزن، عملاء، قيود، مشتريات).

2. **ورشة PVC بدون أي تسجيل دخول**  
   `/api/store` بيرجع **كل** بيانات الورشة المشتركة (عملاء، مشاريع، دفعات، مصروفات) من غير مصادقة. أي شخص عنده الرابط يقدر يقرأ ويعدّل.

3. **بروكسي الجسر في PVC بيسمح الطلب لو Origin/Referer ناقصين**  
   `sameOrigin()` رجوعها `true` في الحالة دي. مع عدم وجود auth، ده يسهّل استدعاء الجسر من برة المتصفح.

4. **ورشة البلسية: دومينين بسلوك مختلف**  
   - `plisse-workshop-sigma.vercel.app` → مفتوح (`AUTH_DISABLED=true`) + سياسات anon CRUD على كل `pls_*`.  
   - `plisse-workshop.vercel.app` (المكتوب في README) → يحوّل لـ `/login`.  
   الناس هتدخل على رابطين مختلفين ويتوهوا، والدومين المفتوح معرض لأي حد.

5. **CORS على APIs جسر المحل = `Access-Control-Allow-Origin: *`**  
   الحماية الوحيدة هي سر المفتاح. والمفتاح موجود في git.

### P1 — تعارض الأرقام وفجوات المزامنة

6. **ثلاث قوانين لمتبقي العميل** (القسم 5) — أهم سبب لشكاوى «المحل مش زي الورشة».

7. **الورشتين write-only على الدفتر**  
   `GET /api/workshop/parties/statement` موجود ومتبني كويس، ومش مستخدم في أي شاشة ورشة. المستخدم في البلسية/PVC عمره ما هيشوف مشتريات المحل أو شغل الورشة التانية.

8. **نجاح محلي ثم فشل جسر**  
   نمط شائع: الحفظ في الورشة يعدّي، وبعدين POST للمحل يفشل، والواجهة تقول إن الفلوس اتحفظت محلياً. مفيش طابور إعادة محاولة. الزر اليدوي «إعادة مزامنة / تحديث كشف المحل» سهل يتتنسي، والبيانات القديمة قبل الجسر ممكن تكون ناقصة في المحل.

9. **نقد منفصل عن الذمة**  
   طلب الخزنة وطلب القيد مش في معاملة واحدة. انقطاع الشبكة في النص يكسّر التوازن بين الخزنة وحساب العميل.

10. **تقارير المحل ناقصة مبيعات الورشة**  
    `/reports` و`/sales` ما بيعرضوش قيود `workshop_sale`. الربحية والمبيعات اليومية في المحل **أقل من الحقيقة** لو الورشة شغالة.

11. **متبقي PVC يتجاهل المشاريع تحت التنفيذ**  
    المحل يسجّل البيع من أول عربون. PVC تخبي المتبقي لحد `done`. فرق متعمّد في الكود (`accounting-scope.ts`) بس مش موضّح للمستخدم.

12. **دمج العملاء لسه حساس**  
    مطابقة التليفون أصلحت دمج الأسماء، لكن: تليفون فاضي = تكرار، تليفون مشترك = دمج غلط. حصلت حالة «عمر» واتصلحت بأدوات split/detach — هتتكرر من غير سياسة تليفون إلزامي.

### P2 — تشغيل، بيانات، صيانة

13. **تخزين PVC = JSON blobs + last-write-wins**  
    مش جداول علائقية. جهازين يعدّلوا في نفس الوقت ممكن واحد يoverwrite التاني. المفتاح `upvc-invoices` موجود ومتساب.

14. **سلسلة migrations في المحل اتكسرت قبل كده**  
    عمود `details` وoverload لـ RPC `apply_cross_app_ledger_entry` سببوا فشل تسجيل من الورشة. فيه زر «إصلاح دفتر الجسر» وmigration `20260815` — علامة إن الإنتاج اتعالج يدوياً أكتر من مرة.

15. **البلسية AUTH_DISABLED = true «مؤقت للتطوير» وهو على الإنتاج**  
    مع migration `20260813_pls_restore_anon_access_dev.sql`.

16. **Connection string لـ Neon ممكن يتتخزن في localStorage** على أجهزة الورشة.

17. **حذف عميل PVC محلي فقط** — الطرف يفضل في المحل.

18. **البلسية ما بتستخدمش** صرف خامات / صندوق وارد / مشتريات خارجية / موردين — الجسر مسموح بيهم في البروكسي من غير ما الواجهة تستخدمهم.

19. **مصروف توريد PVC من غير مشروع** ممكن يتسجل شراء في المحل **من غير** مصروف محلي.

20. **إعادة ضبط المصنع في المحل** بتمسح `workshop_party_map` و`cross_app_ledger_entries` — الورشتين هيفضلوا فاكرين نفس `store_customer_id` القديم.

## 7. التحسينات المطلوبة

مرتبة حسب الأثر، مش حسب حجم الشغل.

### 7.1 توحيد المعنى المالي (الأولوية القصوى للمنتج)

- تعريف واحد معروض للمستخدم: **رصيد المحل = عليه / له**.
- في شاشات عملاء الورشة: اعرض رقمين لو لازم:
  - «متبقي شغل الورشة دي»
  - «رصيد المحل الموحّد» (من `GET /parties/statement`)
- في PVC: إمّا تدخل مشاريع `queued/workshop` في المتبقي (زي المحل)، أو تكتب صراحة «المتبقي المعروض للشغل المكتمل فقط».
- في تقارير المحل: بند واضح «مبيعات/تحصيل PVC» و«مبيعات/تحصيل بلسية» من دفتر الجسر، مش تسيبها برة المبيعات.

### 7.2 قراءة عكسية من المحل

- استدعاء `GET /api/workshop/parties/statement?customer_id=` في صفحة العميل في PVC والبلسية.
- بانر لو `|رصيد المحل − المتبقي المحلي| > تحمل بسيط` → زر «مزامنة».
- المزامنة اليدوية تفضل للبيانات القديمة، لكن الوضع الطبيعي لازم يبقى تلقائي بعد كل حفظ.

### 7.3 طابور مزامنة بدل best-effort

- بعد الحفظ المحلي: صف عملية (`pending`) تتعيد لحد ما المحل يرجع `ok`.
- الخزنة والقيد يتقفّلوا كوحدة منطقية (لو القيد نجح والخزنة فشلت، العملية تفضل pending).
- شاشة «عمليات فشلت» في الإعدادات.

### 7.4 أمن (من غير ما نكسر الاستخدام اليومي)

- شيل الـ fallback من الكود؛ حط `WORKSHOP_BRIDGE_SECRET` على Vercel للورشتين **والمحل**، وروتيشن للمفتاح الحالي لأنه في git.
- قفل `/api/store` في PVC (توكن جهاز أو دخول بسيط).
- رجّع `AUTH_DISABLED=false` في البلسية، طبّق `20260812_pls_drop_anon_access.sql`، ووحّد الدومين على رابط واحد.
- `sameOrigin` يرفض الطلب لو Origin وReferer فاضيين.
- ضيّق CORS جسر المحل على دومينات الورشتين بدل `*`.

### 7.5 جودة بيانات العملاء

- تليفون إلزامي قبل الربط بالمحل.
- تحذير قبل إنشاء عميل جديد لو الاسم قريب من موجود في المحل.
- الورشتين يعرضوا `store_customer_id` وحالة الربط بوضوح (مربوط / فشل / تليفون ناقص).

### 7.6 تشغيل وتنظيف

- README البلسية يتشاف على `plisse-workshop-sigma.vercel.app` (أو يتعمل alias ثابت ويتقفل التاني).
- PVC: ترحيل تدريجي من KV JSON لجداول علائقية، أو على الأقل قفل revision أمنع من last-write-wins.
- تقارير ربحية موحّدة: بيع الورشة − تكلفة خامات «للورشة» − تحصيل.
- متغيرات البيئة: تأكيد `WORKSHOP_BRIDGE_SECRET` على إنتاج الورشتين (دلوقتي fallback).
